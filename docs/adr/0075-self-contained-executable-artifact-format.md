# ADR: Self-contained executable artifact format

- **Status:** Accepted — implemented through the expert-gated `cli-compile` change. Amended 2026-09-14: v2 virtual-store framing (`multidoc` change). Amended 2026-09-25: R2 deploy-time asset embedding (`r2embed` change).
- **Date:** 2026-09-12
- **Supersedes:** None
- **Epic:** `rc-wp01c`

## Context

`camel run` discovers documents from the filesystem, then interpolates environment values, parses, lowers, boots components, and starts routes. A deployment preview needs one executable without making the target install a toolchain or source tree. The release matrix and immutable artifact workflow make an ELF-only section format unsuitable. Route definitions and processors are not a stable serializable artifact boundary, and pre-interpolation documents must retain `${env:}` expressions for deployment-time resolution.

## Decision

V1 uses a fixed 68-byte EOF trailer appended to a copy of the current native Linux executable. The exact footer is `CAMELTR1`, little-endian version/kind/reserved/length fields, BLAKE3, and terminal `CAMELTR1`; its checksum covers ASCII `rust-camel-trailer-v1`, one `0x00` byte, little-endian version/kind/length fields, payload, and manifest, excluding both magic fields and reserved byte. The payload is normalized document text captured before interpolation. A self-detect probe runs before Clap parsing; no recognizable footer means normal CLI behavior, while a marked footer with malformed, unsupported, or corrupt contents fails closed. If truncation removes the terminal marker, the image is indistinguishable from a trailer-free executable and follows normal CLI fallback. The embedded text re-enters the existing discovery/interpolation/lowering/runtime path. The artifact performs no extraction and disables watch.

V1 rejects unsupported compile-time assets explicitly. Runtime endpoint I/O and environment lookup remain deployment-time behavior. The manifest reports runtime version, kind, embedded components, required environment variables without defaults, and listener declarations that may be literal ports or unresolved expressions. BLAKE3 provides integrity, not authenticity; signing is deferred. V1 supports one route document or one job document; cross-compilation, AST/AOT serialization, compiled tests, multi-entry jobs, compression, and long-running route-server artifacts are deferred.

## Amendment: v2 virtual-store framing (2026-09-14)

The `multidoc` change adds trailer version 2. It keeps the `CAMELTR1` family marker. A v2 artifact is `CAMELTR1 || content || index || manifest || footer`. The footer is 76 bytes: `CAMELTR1`, little-endian `u16` version 2, `u8` kind (`1=route`, `2=job`), zero `u8` flags, little-endian `u64` content/index/manifest lengths, BLAKE3, and terminal `CAMELTR1`. The checksum covers ASCII `rust-camel-trailer-v2`, one zero byte, the encoded version/kind/three lengths, content, index, and manifest. It excludes both magic fields and the flags byte.

The content packs a virtual document store: every compile-time document (routes, jobs, `Camel.toml`, includes, selected profiles) as normalized pre-interpolation text, plus a canonical UTF-8 JSON index. Schema ownership is explicit and separate. The index carries `store_schema` (version 1); the manifest carries `manifest_schema` (version 2). The trailer version describes framing only. It never defines store or manifest schema. Readers validate each schema independently and reject unsupported values before boot.

The compiler selects sources only through the explicit `--config <Camel.toml>` and repeated `--profile <name>` options. Without `--config`, it embeds no configuration and selects no profile, and it never discovers ambient configuration. Every resolved source stays inside the selected root. Names normalize to UTF-8 relative `/` paths. Absolute paths, empty or `.` or `..` components, non-UTF-8 names, symlink escapes, duplicate canonical targets, duplicate logical paths, and out-of-root references fail before the output is created. The aggregate normalized embedded bytes stay capped at 16 MiB.

Compatibility stays within the family. A v2 reader decodes a v1 artifact as a one-entry store and preserves v1 behavior. A v1 reader recognizes the marker, does not parse v2, and may reject it as unsupported. This is a safe failure: the marked artifact is never mistaken for a trailer-free executable.

R1 keeps one logical entry point even though the store carries many documents. R3 may extend entry-point cardinality on this store without changing R1 runtime semantics, and R2 (deploy-time asset embedding) may add embedded files to it. Compression, signing, and cross-target compilation stay deferred. The runtime wall is unchanged: no source reads, no globbing, no ambient `Camel.toml`, no extraction, no watch, and artifact arguments stay limited to `--report`, `--help`, `--version`, `--manifest`, and the sanctioned R4 signature-verification surface.

## Consequences

The format is small, dependency-light, and safe for read-only roots. The same executable remains both compiler template and runtime. Compiled artifacts are final immutable outputs; later strip or mutation invalidates the trailer. The artifact trust boundary is the shipped executable, not the deployment source tree. Separate store and manifest schemas let the packed-document model and the operational manifest evolve independently of the trailer framing; unknown schema values fail closed. Boot still performs parse, interpolation, lowering, component boot, and context start, so no boot-speed claim is made before P0 measurement.

## Amendment: R2 deploy-time asset embedding (2026-09-25)

The `r2embed` change lifts part of the v1 asset rejection. `camel compile` embeds deploy-time assets as typed `asset` store entries under the `assets/` logical namespace (`assets/<normalized-relative-path>`, validated by the existing path rules, so document and asset namespaces cannot collide). The store index carries `store_schema` 2; the manifest carries `manifest_schema` 3. The pairing is mandatory and enforced in both directions: a reader accepts manifest schema 3 only with store schema 2, and store schema 2 only with manifest schema 3, because the substitution table and asset classes exist only when both halves evolve together. Unknown-schema diagnostics keep their existing form and precedence — the pairing check runs only when both schemas are known values. Schema-1 stores with manifest-2 bodies stay valid as the un-paired legacy form, and the v1-trailer acceptance is unchanged.

Asset bytes embed verbatim: no BOM removal, no newline conversion, no UTF-8 requirement. Normalization continues to apply to document entries only. The compiler resolves every reference through the existing confinement path (anchor at the selected config root or primary document directory, symlink-aware canonicalization, fail-closed on absolute, traversal, escape, or missing targets), expands `static_dir` trees as a deterministic sorted walk of regular files and fails closed on a symlink inside such a tree, and deduplicates shared canonical targets into one entry while recording every alias spelling in the substitution table. The aggregate bound now covers normalized document bytes plus verbatim asset bytes and moves with `--max-payload-bytes` (default 16 MiB; the fixed constant is gone from enforcement, and the reader stays cap-free).

The index carries a compile-time substitution table: ordered `(document, declared_string) → assets/<path>` entries, each recording the declared string's exact byte span(s) in the normalized document or config entry and the site context — `literal` or `uri`. The runtime replaces only recorded spans, applies them last-offset-first, and percent-encodes `uri`-site values. It never text-searches or canonicalizes declared strings. Before boot, every substituted path must satisfy the substitution path-safety rule: valid UTF-8 with no ASCII control characters at all sites; `literal` sites additionally restrict characters to `[A-Za-z0-9._/+-]`. Violations fail closed before any route or configuration boots.

R2 keeps a per-class consumption carve-out. The default is confinement; the only memory-served class is static files, which the registry serves without touching the filesystem. Disk-written classes (TLS cert/key/CA from document fields and TLS URI parameters, `xslt:` stylesheets, `validator:` schemas, `sql:file:` operands) materialize into a confined per-boot directory under `std::env::temp_dir()`, following the bd `rc-0ks57` confinement discipline: the directory is created exclusively at mode 0700; each file is written once with `create_new` at mode 0600, so a planted symlink at the target path fails the write instead of being followed; the nearest-existing ancestor is re-checked across every created component; writes complete before endpoint spawn; only assets referenced by materialized consumers are written, never the whole store. A guard removes the directory on both graceful shutdown and boot failure. Residue caveat, documented not hidden: `SIGKILL`, `process::exit`, or the in-tree force-exit on a second stop signal (`commands/run.rs:691`, `commands/job/signal.rs:82`) bypasses the drop guard and leaves the per-boot directory behind in the OS temp directory. These classes materialize because their consumers take paths and live in component crates outside this format's seams; flipping a class to a bytes seam is an additive per-consumer follow-up, not a format change.

The runtime resolves asset references through the substitution table plus an in-memory asset registry owned by `camel-bundles` (the `TlsReloadRegistry::global()` singleton pattern). The registry maps `assets/<logical-path>` to bytes, is populated exactly once before boot from positionally paired store and manifest entries — verifying kind, length, and BLAKE3 digest for every pair — and is all-or-nothing: a verification failure leaves it unpopulated. Normal `camel run` never populates it. Digest integrity ownership is split by layer: the decode layer owns the integrity check (the manifest/store agreement compares kind, length, and digest by position, with null-path secret handling, and fails closed at decode); the registry's own mismatch rejection is defense-in-depth. The registry also holds document entries — benign, since positional pairing requires the full lists — and entry `kind` crosses the seam as a `String`, so `camel-bundles` gains no dependency edge toward `camel-dsl`.

Secret-class assets are opt-in. The secret class is exactly the private-key family — the four sealed spellings (`key`, `tlsKey`, `serverKeyPath`, `clientKeyPath`) plus their document-field aliases `keyPath`/`key_path`, all classified by the single `SECRET_ASSET_CLASS` constant (policy.rs). When the collected asset set contains a secret-family entry and `--embed-secrets` is absent, compile exits 2 naming the field and class before any output exists. With the flag, secrets embed normally and the artifact file is written mode 0700 instead of 0755. The manifest gains a per-entry `class` (`public` | `secret`, distinct from the informational `asset_class` name), a top-level `artifact_kind` (`job` | `server`), and `total_embedded_bytes`. Secret-class entries expose digest and length only: their logical path is withheld (`path: null`) in the manifest body and `--manifest` output, and no asset bytes or key material appear in any output or log.

Two authoring-shape rulings bound what R2 accepts. First, document-field `tls:` blocks (bd `rc-7mzdu`): they compile, embed, and materialize, but have no runtime consumer in R2 — a route-level `tls:` key is an unknown DSL field at discovery, so such an artifact never boots. The bootable TLS shape is the `https://` URI parameters (`tlsCert`/`tlsKey`). A client-CA byte-assert against a booting consumer is impossible until the DSL gains a listener TLS shape; deferred (bd `rc-7mzdu`). Second, `static_dir` (bd `rc-epx5i`): the R2-authorable spelling is a step `parameters` entry; a document-level `static_dir:` key compiles into the store but is rejected at discovery as an unknown route field — fail-late, fail-closed.

Classes that stay rejected in R2 are recorded deferrals, not permanent rejections: `wasm:` URI operands and `[security.permissions.<name>]` WASM-provider `path` declarations (bd `rc-2ygmc`), `[beans.<name>]` plugin entries (bd `rc-fjutr`), and file-valued secret fields (bd `rc-0lzxs`). Compression (R6), signing (R4), and cross-target compilation (R7) stay deferred as roadmap milestones, not non-goals.

The sealed amendment checklist (bd `rc-p823t`), each item binding:

- **The limit.** The embedded TLS set is fixed at compile time and changes only by recompiling. No mounted or rotated certificates exist; deploy-side TLS material (mounts, secret stores, rotation) is out of R2 scope.
- **No-host-fallback resolution.** TLS-class references resolve embedded-only at compile AND at runtime. The runtime never probes the host filesystem for a TLS path absent from the store; substitution plus confined materialization is the only resolution path.
- **TLS hot-reload does nothing.** Live-runtime TLS hot-reload has no effect in compiled artifacts. Verification audit (2026-09-25): no watcher or reload path probes the host filesystem against virtual paths in compiled artifacts. Evidence checked: the sealed deployment-unit wall requires no watch or hot reload (`openspec/specs/cli-compile/spec.md`, "Permanent v1 non-goals"; preserved by the `r2embed` delta); both artifact lifecycles boot with `watch: None` (`compile/runtime.rs:879`, `:972`) and the artifact argument parser rejects `--watch` (`compile/runtime.rs:1063`); the runtime module contract states the watcher never activates (`compile/runtime.rs:34`). The only TLS-reload activation is the external control-plane command `RuntimeCommand::ReloadTlsCerts` (`camel-core/src/lifecycle/application/runtime_bus.rs:183`); the artifact runtime issues no such command, and component-side `TlsReloadHandler` registrations (camel-ws `src/lib.rs:276`, camel-http `src/tls_reload.rs:16`) are passive. A reload that did fire would re-read the substituted confined materialization paths — declared virtual paths never reach the runtime, proven by the `round_trip_tls_resolution_never_probes_host_fs` round trip, which boots a listener after the original fixture files are deleted. No probing path was found.
- **Embedded-key risk (accepted).** When an artifact embeds a private key, the artifact IS a secret. `--embed-secrets` gates exactly that decision, and the 0700 artifact mode limits exposure. Signing (R4) protects against tamper, not confidentiality. This is an ACCEPTED risk, owner kennycallado (bd `rc-p823t`, 2026-09-24).
- **R5 pointer and R3 tripwire.** Mounts and rotation are deferred to R5 and tracked by bd `rc-p823t` (closes when mission 243 lands). Tripwire: no long-lived manifest entries ship before the R5 TLS decision, and any artifact that can outlive a short bounded run triggers that decision. The not-taken option — compile warns or rejects server-type consumers in job artifacts — was considered and NOT taken in R2.

# ADR-0090: Pre-1.0 compatibility policy

- Status: Accepted (decided 2026-10-27)
- Source: bd `rc-v6wiz` (epic), bd `rc-65x6i` (implementation)
- Ruling: e_opus plan ranking, 2026-10-27; owner directive 2026-10-27
- Cross-refs: ADR-0024 (hard removal, no deprecation), ADR-0019
  (error-disposition surfaces), ADR-0085, ADR-0087, ADR-0088 (CXF
  opt-ins), ADR-0009 (`http-static` hosting)

## Context

rust-camel is pre-1.0 and has no external users. The README states that
APIs will change. ADR-0024 already applied this position to
`CamelError::Stopped`. It records the owner directive of 2026-06-20:
"no deprecamos xq no tenemos usuarios". No attribute, alias, or legacy
retention was allowed for that removal.

Later changes did not apply the same rule. ADR-0019 keeps the
`ErrorHandlerLayer` / `ErrorHandlerService` shell as a
"backward-compatibility shell for routes that have no `errorHandler`
configured". Other surfaces stay because a test still calls them, or
because a comment calls them legacy. Two kinds of cost follow. Every
removal becomes an argument from first principles, and a real external
contract can be deleted by mistake because no list protects it.

The owner directive of 2026-10-27 (bd `rc-v6wiz`) orders a pre-1.0
shedding wave. The wave must remove surfaces that exist only for our own
history. This ADR supplies the rule that separates those surfaces from
the contracts we must keep.

## Decision

### A compatibility surface may stay for four reasons only

A surface that only older rust-camel code or configuration needs may stay
only when it satisfies one of these categories:

- **(a) External commitment.** A third-party peer or protocol that we do
  not control requires the surface. Example: the external 112 partner that
  still signs with RSA-SHA1 (ADR-0085).
- **(b) Off-by-default security opt-in.** The surface is a switch that is
  off by default and restores a behaviour with a named security or
  interoperability need. Examples: ADR-0085, ADR-0087, ADR-0088.
- **(c) Wire or format contract with a component not shipped in
  lockstep.** A published artifact, a bridge, or a peer decodes bytes that
  we emit, or emits bytes that we decode. Example: proto3 `UNSPECIFIED`
  is the wire default of an enum and has a defined boolean mapping
  (ADR-0086).
- **(d) Specification requirement citing (a)-(c).** A normative
  specification requirement names one of the categories above and
  therefore makes the surface part of a contract.

Every other compatibility surface is deleted before 1.0.

### Deletion, not hiding

- Code reached only by tests or benches is not compatibility. Tests
  exercise production surfaces. If only a test or a bench calls an item,
  the item is deleted and the test is ported to the surface that replaced
  it.
- `#[deprecated]` is not allowed in this workspace. An item is either
  kept as current API with no attribute, or deleted. A warning does not
  protect a user, and it does not remove the code.
- Hiding is not deletion. `#[doc(hidden)]`, a default-off feature flag,
  and a test-only `cfg` attribute do not satisfy this policy.
- The word "legacy" MUST NOT name an internal implementation. It may
  describe an external peer or protocol that is genuinely old, as in
  ADR-0085. `FilterService` is not "legacy". It is a duplicate spelling
  of `FilterSegment`, and it is deleted.

### A removal carries a tombstone

A removed configuration key, URI form, or artifact format MUST fail at
load with an error that names the replacement. The failure is a tombstone,
not a silent fallback and not a warning. For example, the `[jobs] dir`
alias names `[jobs] dirs`, and a removed v1 compiled artifact names the
`camel compile` command that produces the current artifact.

A removal MUST NOT take away a capability. It may remove only an
ambiguous or duplicate spelling of a capability (bd `rc-v6wiz`). The
`http-static` path-as-dir form is therefore kept. It is the natural way to
point at a directory to serve, it exists since the first commit, and it is
not a compatibility case (bd `rc-aigiv`).

### Kept-surfaces register

The register is the complete list of surfaces that this policy allows to
stay for compatibility. A surface without a register entry has no
compatibility claim. Adding an entry requires maintainer approval. The
entry names the surface, its category, and the ADR or bd citation that
justifies it.

| Surface | Category | Citation |
| --- | --- | --- |
| JMS `UNSPECIFIED` to boolean health mapping | (c) | ADR-0086; proto3 enum default 0 is a real wire value |
| `http-static` path-as-dir | primary surface, not a compatibility case | bd `rc-aigiv`; reclassified 2026-10-27 |
| CXF inbound SHA-1 allow-list | (b) | ADR-0085 |
| CXF expired pinned certificate acceptance | (b) | ADR-0087 |
| CXF Timestamp freshness window | (c) | ADR-0088; external WS-Security peers set `Created` |

The `http-static` row records a reclassification. It has no category
because it is not a compatibility surface. It stays because it is the
primary spelling of a capability. The row prevents a future reader from
deleting it as legacy.

## Consequences

The workspace becomes `#[deprecated]`-free after this wave. The two
remaining attributes are deleted, and a new attribute fails review. A
proposed `lint-no-deprecated` xtask makes that failure automatic if the
same wave adopts it. Until then, review is the gate.

Crate API removals are acceptable in a 0.x minor release (bd `rc-v6wiz`).
Configuration, URI, and artifact tombstones protect the user data that can
exist locally: route URIs, `Camel.toml`, compiled artifacts, and cached
bridge binaries.

The register stays short by design. A surface that needs a fifth category
is a signal to reopen this ADR. It is not a reason to add a category
informally.

Removal reduces the code we maintain and the spellings a user must
understand. It also removes the tests that only exercised the removed
spelling. Each wave port must preserve the behaviour under the surviving
surface, as ADR-0024 requires for its own removal.

## Alternatives rejected

| Alternative | Why rejected |
| --- | --- |
| Keep a `#[deprecated]` grace period | Pre-1.0 has no users to migrate. A compiler warning does not reach an operator who holds a route URI or a `Camel.toml`. The code and its tests still cost maintenance. |
| Keep surfaces that only tests use | Tests must exercise production surfaces. A test-only surface proves nothing about the route a user runs. |
| Delete without tombstone errors | Route URIs, configuration, and compiled artifacts can exist on disk. A silent break hides the replacement from the operator. |
| Gate old spellings behind a feature flag | A flag hides a duplicate. It does not remove it, and it adds a build matrix cell. |
| Use "legacy" as a label for our own code | The label hides the duplicate's owner and makes the surface look permanent. Name the replacement instead. |
| Add categories case by case | The four categories are the complete test. Case-by-case additions return the decision to argument and lose the register's value. |

## Evidence and limits

The baseline of 2026-10-27 supports the need for the policy. The
`camel-processor` crate has 59 `impl ... Service<` matches. Seven EIP
Service types (`FilterService`, `ChoiceService`, `LoopService`,
`ThrottlerService`, `SplitterService`, `MulticastService`,
`LoadBalancerService`) have no hits in `openspec/specs/`, so no
specification requires them. The workspace has three `#[deprecated]`
sites. The shedding wave deletes the seven Service types and the two
attribute sites that are not prose.

The register is normative only for the surfaces that it lists. A surface
that is absent from the register has no compatibility claim, even if an
old comment calls it legacy.

The policy governs code, configuration, and artifacts that we own. It does
not authorize a break of a published bridge protocol. Category (c) covers
that case, and a component that ships on a different cadence must keep its
contract until both sides can move together.

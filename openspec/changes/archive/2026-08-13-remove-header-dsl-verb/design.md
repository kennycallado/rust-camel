# Design: remove-header-dsl-verb

## Approach

Thread a `remove_header` verb through the existing declarative-step pipeline,
mirroring `set_header` at every layer. The new verb has a single field
(`key: String`) — simpler than `set_header` (which carries value/language/
source/simple/rhai/jsonpath/xpath). The pipeline layers, in order:

1. **AST** (`route_ast.rs`): `RouteDslStep::RemoveHeader(RemoveHeaderStep)` +
   `RemoveHeaderStep { remove_header: RemoveHeaderData }` +
   `RemoveHeaderData { key: String }`. Both structs carry the exact same
   derive set as `SetHeaderStep`/`SetHeaderData`:
   `#[cfg_attr(feature = "schema", derive(schemars::JsonSchema, ts_rs::TS))]`
   + `#[derive(Deserialize, Debug, Clone)]` + `#[serde(deny_unknown_fields)]`.
   No variant-level serde rename (`RouteDslStep` is `#[serde(untagged)]`, so
   the YAML key comes from the inner `remove_header` field name).
2. **Kind registry** (`contract.rs`): add `DeclarativeStepKind::RemoveHeader`
   variant (with serde rename `remove_header`). Then append it to
   `MANDATORY_DECLARATIVE_STEP_KINDS` (const array, currently 38 → 39) AND
   update the length assertion `assert_eq!(..., 38)` → `39`. Also append to
   `YAML_IMPLEMENTED_MANDATORY_STEPS` in `yaml.rs` (same array, 38 → 39) so
   the `assert_contract_coverage` const-eval check passes. Finally, add a
   `RemoveHeader` arm to `DeclarativeStep::kind()` in `model.rs:619`.
3. **Lowered model** (`model.rs`): `DeclarativeStep::RemoveHeader(
   RemoveHeaderStepDef { key: String })` + `RemoveHeaderStepDef` struct.
4. **YAML parse** (`yaml.rs`): match arm that lifts `RouteDslStep::RemoveHeader`
   → `DeclarativeStep::RemoveHeader`, with empty-key validation (same guard as
   `set_header` at L613).
5. **Compile** (`compile.rs`): `DeclarativeStep::RemoveHeader` →
   `BuilderStep::DeclarativeRemoveHeader { key }`. Also register in
   `declarative_step_name()` (L1538) + validation (L1801).
6. **BuilderStep** (`route_definition.rs`, camel-core):
   `BuilderStep::DeclarativeRemoveHeader { key: String }`.
7. **Step compiler** (`step_compilers/core.rs`): branch that instantiates
   `camel_processor::RemoveHeader::new(IdentityProcessor, key)`.
8. **Processor** (`camel-processor/src/remove_header.rs`, NEW): a
   `RemoveHeader<P>` struct implementing `Service<Exchange>` that calls
   `exchange.input.headers.remove(&self.key)` then delegates to inner.
   Mirrors `SetHeader<P>` (set_header.rs:52-76) exactly, swapping
   `insert` for `remove`.
9. **Schema** (type-derived, not hand-edited): the route JSON schema is
   generated by `schemars::schema_for!(RouteDslSchemaEnvelope)` in
   `generate_dsl_schema()` (`scripts/xtask/src/main.rs:1381`), which derives
   the schema entirely from the `RouteDslStep` enum's `JsonSchema` impls.
   Adding the `RemoveHeader` variant WITH the `schemars::JsonSchema` +
   `ts_rs::TS` cfg_attr derives (see step 1) auto-includes it in the generated
   schema — no hand-edited step list exists. Regen: `cargo run -p xtask --
   schema` (writes `schemas/dsl/route-schema.json` only), then manually copy:
   `cp schemas/dsl/route-schema.json crates/camel-lint/schema/route-schema.json`.
   Verify: `cargo run -p xtask -- schema --check` (zero drift on both files).

The processor is input-only, matching `SetHeader` (the direct analog). See
"Alternatives considered" for why output-header removal is excluded.

## Affected crates

- **camel-dsl**: route_ast.rs (AST variant + 2 structs, with
  `schemars::JsonSchema`/`ts_rs::TS` cfg_attr derives matching SetHeaderStep),
  contract.rs (DeclarativeStepKind variant + MANDATORY_DECLARATIVE_STEP_KINDS
  38→39 + length assertion), model.rs (DeclarativeStep variant + def struct +
  kind() arm), yaml.rs (YAML_IMPLEMENTED_MANDATORY_STEPS 38→39 + parse +
  empty-key guard), compile.rs (lower + name + validation).
- **camel-core**: route_definition.rs (BuilderStep variant),
  step_compilers/core.rs (compile branch).
- **camel-processor**: NEW remove_header.rs (RemoveHeader processor +
  RemoveHeaderLayer + tests), lib.rs (mod declaration).
- **schemas/dsl/route-schema.json** (regenerated by `cargo run -p xtask --
  schema`, auto-derives from RouteDslStep JsonSchema) +
  **crates/camel-lint/schema/route-schema.json** (embedded copy, updated
  manually via `cp schemas/dsl/route-schema.json
  crates/camel-lint/schema/route-schema.json`), verified by
  `cargo run -p xtask -- schema --check`.

## Architecture boundaries

This change respects the data/control plane boundary (ADR-0032). Header
removal is a pure data-plane mutation on exchange input — the same category as
`set_header`. No control-plane surface, no endpoint/component interaction, no
trusted-config-vs-untrusted-data crossing: the `key` comes from operator route
config (trusted), and the removal target is runtime exchange data (untrusted
but only read for matching, never executed). The verb flows through the
standard DSL → compile → runtime pipeline without touching the component or
services layers. It references the PipelineOutcome contract (ADR-0024) only
indirectly — the processor returns `Result<Exchange, CamelError>` like every
other `Service<Exchange>`.

## Alternatives considered

- **Output-header removal (InOut semantics)**: The bd suggested removing from
  both input and output message headers. Rejected: no existing processor
  mutates `output.headers` (SetHeader is input-only), and introducing output
  mutation would require new InOut-detection infrastructure and a divergent
  pattern. Apache Camel 3.x itself moved toward a single-message model. YAGNI
  for the single-key demo use case.
- **`remove_headers` glob/pattern variant**: Deferred to a follow-up bd issue.
  The single-key verb is the minimum viable fix; a glob variant needs a
  matching strategy (substring? regex? fnmatch?) which is a separate design
  decision.
- **Inline processor in step_compilers (no camel-processor struct)**: Rejected
  for consistency — every declarative header verb (SetHeader,
  SetHeaderIfAbsent, DynamicSetHeader) has a dedicated processor struct with
  tests. RemoveHeader follows the same discipline.

# Design: r2embed

## Approach

Reuse the CAMELTR1 v2 framing unchanged: `CAMELTR1 || content || index || manifest || footer`. The trailer already carries content, index, and manifest as independent length-delimited sections, so asset embedding extends the two JSON schemas, not the framing. Trailer version stays 2; `store_schema` bumps to 2 and `manifest_schema` bumps to 3, keeping the trap-3 rule that no schema meaning rides the trailer version byte.

**Store extension.** `camel-dsl`'s canonical store model gains `StoreEntryKind::Asset` plus a per-entry `asset_class` string and `store_schema: 2`; readers reject unknown schemas and unknown kinds fail closed as today. Asset entries are keyed `assets/<normalized-relative-path>` so document and asset namespaces cannot collide, and re-verify R1 path rules (UTF-8, `/` separators, no absolute, `.`/`..`, or escape). Asset bytes embed verbatim: no BOM strip, no newline conversion, no UTF-8 requirement — binary safety is the point of DER-capable asset paths. Assets write in canonical path order interleaved with documents in the same content section; the aggregate-byte accounting includes raw asset bytes.

**Substitution table.** The store index gains a compile-time `substitutions` table: an ordered list of `(document, declared_string) → asset logical path` mappings, one entry per distinct declared spelling in each document, each entry recording its exact site — the byte span(s) in the normalized document or config entry where that declared string occurs, captured at compile time. Deduplication by canonical target means alias spellings (`./ca.pem` and `tls/ca.pem` resolving to one file) map to one asset entry while the table keeps every alias spelling pointing at that single entry. At runtime the table is the only resolution path: the engine replaces exactly the recorded byte spans — applied last-offset-first so earlier offsets and line numbers stay stable — and SHALL NOT text-search for declared strings, canonicalize, re-resolve, or re-read them from disk. Values written into a URI are percent-encoded so they round-trip consumer decoding (`camel-validator` percent-decodes its schema path before use, `config.rs:62`); a materialization path containing URI-reserved characters or whitespace that cannot be encoded safely fails before boot with a named diagnostic. This is what makes the post-compile decoy scenario meaningful — a file appearing at the originally declared path after compile is unreachable because runtime never re-resolves declared strings.

**DECIDED — embedded-only TLS asset resolution, no host fallback (sealed ruling bd rc-p823t).** Every TLS-class reference — document `tls` blocks (`cert`/`key`/`client_ca`), the `tlsCert`/`tlsKey` HTTP/WS URI parameters, and the gRPC `serverCertPath`/`serverKeyPath`/`clientCaPath`/`caCertPath`/`clientCertPath`/`clientKeyPath` family — resolves ONLY to embedded virtual-store entries. At compile time a missing or unresolvable path is the existing compile FAIL (reject-missing, task 1.2); at RUNTIME there is NO host-filesystem fallback: resolution goes exclusively through the embedded store and the confined per-boot materialization, and the originally declared host path is never probed. A file present at the declared path after compile is unreachable, and a file absent there changes nothing. Rationale: a fallback would reintroduce the ambient-filesystem read the substitution table exists to eliminate, and an unreviewed host-mount mechanism cannot ship inside R2. The reference syntax stays unversioned and unprefixed so R5 can add explicit `host:`/`env:` prefixes without a breaking format change.

**Asset enumeration.** The compile-time policy walk in `camel-cli/src/compile/policy.rs` flips from rejecting the R2 matrix to collecting asset references, keeping its exact TLS-context scoping for document fields (`cert`/`key`/`client_ca` count as assets only under `tls`/`ssl`/`rest`/`mcp` ancestors) and its exact field spellings plus camelCase/path aliases. Collected classes:

- certificate, private key, and client-CA files in TLS/listener document fields;
- TLS endpoint URI parameters: `tlsCert`/`tlsKey` on HTTP and WS endpoint URIs (`camel-component-http/src/lib.rs:805`, `camel-component-ws/src/config.rs:96`), and the gRPC family `serverCertPath`/`serverKeyPath`/`clientCaPath` (server side) and `caCertPath`/`clientCertPath`/`clientKeyPath` (client side) (`camel-component-grpc/src/config.rs:484-490`). Absolute path values and `${env:}` values in any of these parameters fail closed at compile time — an embeddable artifact needs a root-relative, compile-known path;
- `xslt` fields and `xslt:` URI operands; `xsd` fields and `validator:` URI operands;
- `sql:file:<path>` URI operands (there is no `sql` document field; inline-query `sql:` endpoints without the `file:` operand stay permitted — they carry runtime datasource queries, not assets);
- `static_dir`/`staticDir` trees.

The document `wasm` field is a security-policy REGISTRY NAME (`DeclarativeSecurityPolicy::Wasm` resolves it through `SecurityPolicyRegistry::get`, `camel-dsl/src/compile.rs:164-179`), not an embedded asset — it stays ordinary document data and leaves the matrix. There is no `plugin` document field; the former document-field check for `plugin` is dropped. The walk keeps rejecting with named diagnostics: `wasm:` URI operands (R2-only deferral recorded in bd — `validate_and_resolve_path`, `camel-component-wasm/src/lib.rs:85-116`, requires a relative path inside `base_dir`, which is project root = CWD for both artifact kinds, so the confined per-boot directory can never satisfy it, and the job runtime seam sits outside this lease; revisit with a route-only `project_root` redirect), file-valued secret fields, dynamic `${env:}` placeholders inside asset fields, absolute paths in TLS URI parameters, and nested-document route sources.

**DECIDED — `Camel.toml` plugin and security-policy WASM declarations fail closed at compile.** An embedded `Camel.toml` containing `[beans.<name>]` `plugin` entries (bean plugins load `<cwd>/plugins/<name>.wasm` at runtime — a current-directory-relative load that cannot be confined or substituted in-lease) or `[security.permissions.<name>]` WASM-provider `path` declarations (`WasmSecurityPolicyConfig.path`, consumed by `WasmSecurityPolicy::new(<path>, …)` at `camel-component-wasm/src/security_policy.rs:122`, a path-taking constructor) exits 2 with a named diagnostic and no output. Rationale: the only bytes seam for the security-policy constructor lives inside `camel-component-wasm` (outside this mission's zone lease), and bean plugin resolution is anchored to the deployment working directory by contract. Alternative considered and rejected for R2: embed the module bytes and materialize them with a substituted path rewritten into the embedded config before security boot. Rejected because security policies are boot-critical trust anchors — writing them into a shared temp directory before the confinement guard chain is exercised widens the trust boundary the materialization discipline exists to shrink, and it would silently diverge from the `<cwd>/plugins/` resolution convention beans users deploy with. Both classes are recorded deferrals to the wasm-policy owner (bd), not permanent rejections.

`sources.rs` resolves every collected reference with the R1 confinement rules (symlink-aware canonicalization, reject escape/missing), expands static directories as a deterministic sorted walk of regular files, and deduplicates by canonical target so two references to one CA embed one entry. A symlink encountered INSIDE a static tree fails closed with a named diagnostic (it is not silently ignored — silent skipping could hide a pivot out of the tree). Asset logical paths anchor to the selected `--config` root, or the primary document directory when no root applies, exactly like route sources.

**Configurable cap.** `camel compile` gains `--max-payload-bytes <BYTES>` (u64 > 0, default 16777216). Enforcement moves with the knob at the single aggregation point: normalized document bytes plus raw asset bytes must not exceed the value, else compile exits 2 naming the total and the cap. The reader gains no cap; decode already validates lengths against file bounds and checksum.

**Manifest schema 3.** `embedded_files` entries gain `asset_class` (the class NAME, e.g. `certificate`; null for documents) and `class` — the secret-material marker `"public"` | `"secret"`, a field distinct from `asset_class` (sealed ruling bd rc-p823t); documents are implicitly public — and keep path, kind, byte length, and BLAKE3 digest; a new `total_embedded_bytes` records the aggregate; a new top-level `artifact_kind` records `"job"` | `"server"`, derived from the trailer kind (route → `server`, job → `job`) so operators can tell a bounded-run artifact from a listener artifact without booting. `--manifest` prints all of it without booting. Readers accept manifest schemas 2 and 3 and fail closed on others.

**DECIDED — secret manifest entries expose digest and length only (sealed ruling bd rc-p823t).** Manifest entries for secret-class assets (`class: "secret"` — exactly the private-key family) expose ONLY the classification fields, byte length, and BLAKE3 digest; the logical path is withheld (null) in the manifest body and `--manifest` output, and no asset bytes or key material ever appear in `--manifest` output, compile output, or logs. The store index retains the logical path because the substitution table needs it at runtime; the manifest is operator-facing metadata and leaks nothing reversible.

**DECIDED — R3 tripwire on artifact kind (sealed ruling bd rc-p823t).** `artifact_kind` exists NOW, in R2, as a tripwire: R3 MUST NOT ship long-lived manifest entries before the R5 TLS decision exists, and any artifact that can outlive a short bounded run triggers that R5 decision. The optional compile-side measure — warning about or rejecting server-type consumers in job artifacts — is NOT taken in R2; it is recorded here as a considered-and-not-taken option for the R3 owner.

**DECIDED — schema pairing (nit a).** Store schema 2 requires manifest schema 3. A store-2 index paired with a manifest-2 body is a format error: readers reject the pairing in both directions (store 2 + manifest ≠ 3, and manifest 3 + store ≠ 2), because the substitution table and asset classes only exist when both halves evolve together. Schema-1/manifest-2 R1 artifacts remain valid as the un-paired legacy pair.

**In-memory serving.** A new `camel-bundles` module owns a process-global, read-only asset registry (the `TlsReloadRegistry::global()` singleton pattern): the compiled-artifact runtime populates it from decoded asset entries before boot, verifying every BLAKE3 digest at load and failing closed on mismatch or duplicate. Normal `camel run` never populates it, so nothing leaks ambiently. This registry is the virtual FS of record for memory-served classes. Because the registry is process-global, registry-test isolation is fixed by DECIDED plan-flag choice: one populating test per dedicated test binary (`cargo test` spawns one process per integration-test target, so the populating test runs alone in its own process; emptiness assertions live only in binaries that never populate), and the public API exposes `is_populated()` so tests assert isolation explicitly instead of resetting global state. No injectable registry instance is added behind the global.

**Per-class consumption matrix.** The default for R2 is confinement; the ONLY memory-served class is static files. Every module-consuming seam that exists today takes a path and lives in a component crate outside this mission's zone lease, so those classes materialize.

| Class | Runtime seam | R2 disposition |
|---|---|---|
| cert / key / client CA — TLS-context document fields | `ServerTlsSource` reads PEM paths inside `camel-component-api` consumers | Materialized — legacy path reader, out of lease |
| cert / key — endpoint URI params (`tlsCert`/`tlsKey` on http/ws; gRPC six-field family) | same `ServerTlsSource` path readers, fed from parsed URI params | Materialized — same legacy path readers |
| `wasm:` URI operand modules | `camel-component-wasm` loads the module path (path-taking constructor, `security_policy.rs:122`) | Compile-time FAIL CLOSED — R2-only deferral recorded in bd (see the asset-enumeration rationale) |
| `xslt:` stylesheets | `camel-xslt` resolves the stylesheet path | Materialized — legacy path reader, out of lease |
| `validator:` / `xsd` | `camel-validator` resolver reads the file, then registers bytes via `XsdBridgeBackend::register(xsd_bytes)` | Materialized — legacy path reader, out of lease |
| `sql:file:` operands | `camel-sql` reads the file at runtime (`camel-component-sql/src/config.rs:294`) | Materialized — legacy path reader, out of lease |
| `[security.permissions.<name>]` WASM provider `path` | path-taking constructor in `camel-component-wasm` | Compile-time FAIL CLOSED (DECIDED above); deferral recorded in bd |
| `[beans.<name>]` `plugin` | loads `<cwd>/plugins/<name>.wasm` at runtime | Compile-time FAIL CLOSED (DECIDED above); deferral recorded in bd |
| static dirs | no in-tree consumer serves them yet; entries stay registry-readable | Memory-served — the only memory-served class |

Security-policy WASM, where a future mission lands it, is disk-written via the path-taking constructor — it is not a memory-served class; in R2 it never reaches an artifact because compile fails closed.

**DECIDED — runtime swap point (route and job).** The substitution-and-materialization step runs in `compile/runtime.rs` after decode and BEFORE kind dispatch, so both artifact kinds are covered from in-lease code. Seam evidence: `compile/runtime.rs:443-446` dispatches `TrailerKind::Route` → `run_embedded_store_route` (which builds a `LifecycleSpec` and calls `crate::commands::run::drive_lifecycle`, `commands/run.rs:249`) and `TrailerKind::Job` → `crate::commands::job::run_embedded_job_store(store, report)` (`commands/job/mod.rs:1403`, outside the lease). The store is passed by value from in-lease code in both branches: rewriting only the substitution table's recorded byte spans in document bytes and config entries inside `compile/runtime.rs` before dispatch means neither `drive_lifecycle` nor `run_embedded_job_store` needs modification — both consumers receive already-substituted data. No job-specific swap point exists or is needed; the lease boundary is respected without a deferral.

**Materialization.** The shim follows the bd `rc-0ks57` file-ancestor-confinement discipline. Concretely: the per-boot directory is created under `std::env::temp_dir()` with a random name using the `tempfile` crate (already a workspace dependency, root `Cargo.toml:197` — no new deps) so the directory itself is created mode 0700 and exclusively; each file is written once before endpoint spawn with `create_new` (exclusive create — an existing or symlinked name at the target path fails rather than being followed) at mode 0600; nearest-existing-ancestor containment is re-checked across every created component; only assets referenced by materialized consumers are written, never the whole store. A guard owned by `compile/runtime.rs` removes the directory on BOTH graceful shutdown and boot failure (any early return between materialization and lifecycle handoff drops the guard). Caveat, documented not hidden: `SIGKILL`, `process::exit`, or the in-tree force-exit on a second stop signal (`commands/run.rs:691`, `commands/job/signal.rs:82`) bypasses the guard and leaves residue in the OS temp directory; operators who need stronger guarantees get them when the class flips to a bytes seam. Only materialized classes require a writable temp location; their absence (or presence) decides the read-only contract scenarios below.

**DECIDED — secret embedding requires explicit opt-in (sealed ruling bd rc-p823t).** `camel compile` gains `--embed-secrets` (the `--max-payload-bytes` precedent: an always-expressible compile flag that needs no configuration root). When the collected asset set contains any secret-family entry — exactly the private-key class: the `key` document field and the `tlsKey`, `serverKeyPath`, and `clientKeyPath` TLS URI parameters — compilation WITHOUT the flag fails closed with a named diagnostic naming the field and the secret class, and no artifact is written. Alternative considered and rejected for R2: the same opt-in expressed as a `Camel.toml` key — rejected because the flag is expressible in every compile invocation without a config root, mirroring `--max-payload-bytes`; the Camel.toml-key spelling is revisited at R5 together with the `host:`/`env:` syntax decision. Accepted risk, named by the owner (kennycallado, bd rc-p823t, 2026-09-24): an artifact embedding a private key IS a secret — the key is extractable from the artifact's virtual store; signing (R4) protects against tampering, NOT against confidentiality.

**Secret-material artifact mode.** The 0700 write mode is conditioned on secrets actually being embedded: when secret-family entries are present in the compiled aggregate — which, by the opt-in gate above, can only happen WITH `--embed-secrets` — the artifact file is written with mode 0700 instead of the default 0755 (`commands/compile.rs` write path, currently `Permissions::from_mode(0o755)`); artifacts without embedded secrets keep 0755. The opt-in-absent + secret-present case never reaches the write site — it fails at compile. Client-CA material is public, not in the family, and never triggers 0700; file-valued secret fields fail at compile and can never be embedded. The mode is chosen at the single write site from the store's class inventory.

## Affected crates

- `camel-cli`: asset enumeration (document fields, URI operands, TLS URI parameters), confinement, substitution table, embedded-only TLS resolution (no host fallback), store/manifest schema bumps with pairing, cap knob, `--embed-secrets` opt-in gate, secret-class 0700 artifact mode, artifact runtime population/substitution/materialization guard, compile and round-trip tests.
- `camel-dsl`: additive store-model extension (`StoreEntryKind::Asset`, `asset_class`, `store_schema: 2`, index `substitutions` table); no discovery change.
- `camel-bundles`: asset registry module, materialization support seams.
- Component crates: unchanged. Flipping a materialized class to a memory seam is an additive per-consumer follow-up.

## Architecture boundaries

`camel-cli` owns packaging, decode, substitution, and boot injection. `camel-dsl` owns the canonical store model. `camel-bundles` owns the registry. Components keep their existing file-reading construction sites; they are reached through the substitution table plus confined materialization, not source edits. The runtime wall holds: no discovery, no globbing, no ambient `Camel.toml`, no watch, no canonicalization of declared asset strings; the read-only-deployment contract is amended to permit only the confined materialization carve-out plus an explicitly requested report.

**ADR note for Phase 4 — the amendment carries the sealed 5-item checklist (bd rc-p823t):** (i) the limit — the embedded TLS set is fixed at compile time and changed only by recompiling; no mounted or rotated certificates; deploy-side TLS material (mounts, secret stores, rotation) is out of R2 scope. (ii) The resolution rule — TLS-class references resolve embedded-only, with NO host fallback at compile or runtime. (iii) The reload statement — live-runtime TLS hot-reload does NOTHING in compiled artifacts — PLUS a verification step: audit that NO watcher/reload path probes the host filesystem against virtual paths, citing the existing artifact no-watch evidence/tests; if the audit finds a probing path, file a bd issue discovered-from `rc-mval9` and surface it to the conductor — do not silently patch out-of-lease code. (iv) The embedded-key risk — an artifact embedding a private key IS a secret, the `--embed-secrets` opt-in gates exactly that, and the risk is documented as accepted with the owner named (kennycallado, bd rc-p823t, 2026-09-24). (v) The R5 pointer — mounts and rotation are deferred to R5, tracked by bd `rc-p823t`, which closes when mission 243 lands; the R3 tripwire (no long-lived manifest entries before the R5 TLS decision; any artifact that can outlive a short bounded run triggers that decision) is recorded in the same amendment. The amendment must state all five so R2 is not read as a TLS-operations feature.

## Phases

### Phase 1: Asset store schema and compile-time embedding (w_heavy)
- **Goal:** Embed confined asset bytes as typed store entries under schema 2 with the substitution table.
- **Dependencies:** R1 store/trailer codecs, policy walk, BLAKE3, `tempfile` (workspace).
- **Externally-visible types/interfaces:** `StoreEntryKind::Asset`, `asset_class`, `store_schema: 2`, index `substitutions` table, compile acceptance of the revised asset matrix.
- **Deliverable:** Artifacts containing assets with deterministic bytes, confinement, URI-parameter TLS collection, and fail-closed `beans`/`permissions` checks.
- **Exit-criteria:** Store codec, enumeration, confinement, static expansion (symlink fail-closed), dedupe-with-aliases, TLS URI-param collection/rejection, and compile CLI tests pass.

### Phase 2: Cap knob, secret opt-in, and manifest schema 3 (w_balanced)
- **Goal:** Configurable aggregate cap, `--embed-secrets` opt-in gate with the 0700 secret-bearing artifact mode, per-asset digest manifest with pairing, `class`/`artifact_kind` fields, and digest-only secret exposure.
- **Dependencies:** Phase 1 asset entries.
- **Externally-visible types/interfaces:** `--max-payload-bytes`, `--embed-secrets`, `manifest_schema: 3` (paired with `store_schema: 2`), `total_embedded_bytes`, per-asset `class` (`public`|`secret`), top-level `artifact_kind` (`job`|`server`), artifact mode 0700 for embedded secret classes.
- **Deliverable:** Cap enforcement at the single aggregation point; the opt-in gate failing closed without the flag when a secret-family asset is present; manifest reporting digests, total size, classes, and artifact kind with secret entries reduced to digest + length; artifact write mode following the embedded class inventory.
- **Exit-criteria:** Under/at/over-cap tests, opt-in fail-without-flag/pass-with-flag tests, pairing-rejection tests, manifest digest/class/artifact-kind tests, digest-only secret-exposure tests, and artifact-mode tests pass; reader accepts schemas 2 and 3.

### Phase 3: Registry, substitution, materialization, and round trip (w_heavy)
- **Goal:** Serve static files in memory; substitute and materialize documented legacy classes under confinement for both artifact kinds.
- **Dependencies:** Phases 1 and 2.
- **Externally-visible types/interfaces:** `camel-bundles` asset registry; `compile/runtime.rs` substitution + materialization guard (covers route and job dispatch).
- **Deliverable:** Compile → boot → asset-readable round trip per class with no bulk extraction; read-only deployment contract scenarios.
- **Exit-criteria:** Per-class round-trip, no-temp-file (static), confinement/cleanup incl. boot failure (materialized), read-only-root scenarios, decoy, digest-mismatch, and registry-isolation tests pass.

### Phase 4: Documentation and contract alignment (docs)
- **Goal:** Record asset vocabulary, schema evolution + pairing, the materialization carve-out, the 0700 secret-artifact rule, and the no-mounted-certs limit.
- **Dependencies:** Phases 1–3 behavior.
- **Deliverable:** ADR 0075 amendment, context-map and crate-context terms.
- **Exit-criteria:** Citation and OpenSpec validation pass; docs do not claim compression, signing, cross-target compilation, or consumer-crate byte seams that do not exist, and do not present R6/R4/R7 deferrals as permanent non-goals.

## Alternatives considered

- **Extract the whole store at boot:** rejected — read-only roots and the no-extraction wall.
- **Registry-aware constructors in component crates:** rejected this mission (outside the zone lease); recorded as additive per-consumer follow-ups.
- **Embed + materialize `[security.permissions]` policy modules and bean plugins with substituted paths:** rejected for R2 — see the DECIDED block; trust-boundary and cwd-resolution rationale; deferral recorded in bd.
- **Ignore symlinks inside static trees:** rejected (nit ruling) — fail closed instead; silent skips hide pivots.
- **Base64 assets as schema-1 text entries:** rejected — dishonest typing, size inflation, no class metadata.
- **Reader-side cap encoded in the artifact:** rejected — the cap is compile-time policy; encode/decode bounds already suffice.
- **Static dirs as one tarball entry:** rejected — loses per-file digests and direct registry reads.
- **New trailer family or trailer-version bump:** rejected — framing is unchanged and schemas evolve independently.
- **Job-specific swap point inside `commands/job/**`:** rejected — outside the lease and unnecessary; the store is rewritten in-lease before the by-value dispatch (see DECIDED swap point).
- **Secret opt-in as a `Camel.toml` key instead of a compile flag:** rejected for R2 (sealed ruling bd rc-p823t) — the flag is always expressible without a config root, mirroring `--max-payload-bytes`; the config-key spelling is revisited at R5.
- **Host-filesystem fallback for TLS paths absent from the store:** rejected (sealed ruling bd rc-p823t) — embedded-only resolution with no host fallback; a fallback would reintroduce ambient reads and pre-empt the R5 `host:`/`env:` syntax decision.

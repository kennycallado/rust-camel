# Proposal: r2embed

## Why

`camel compile` currently rejects every deploy-time asset class, so a route or job that deploys with TLS certificates, XSLT stylesheets, XSD schemas, SQL files, or static content cannot become a deployment-equivalent artifact: it compiles only by removing the assets it depends on. This change is R2 of the compile roadmap (bd `rc-mval9`, epic `rc-rye74`): discover those assets at compile time, embed them in the R1 virtual document store, and serve them to runtime consumers from memory or from a confined per-boot materialization with no bulk extraction. The fixed 16 MiB payload cap becomes configurable here, where asset bytes first join the aggregate.

## What Changes

- Enumerate deploy-time assets at compile time from route/job documents and `Camel.toml` declarations: certificate, private-key, and client-CA files in TLS and listener contexts (`cert`/`key`/`client_ca` spellings under `tls`/`ssl`/`rest`/`mcp` ancestors) AND in endpoint URI parameters (`tlsCert`/`tlsKey` on HTTP and WS endpoints; gRPC `serverCertPath`/`serverKeyPath`/`clientCaPath` on server endpoints and `caCertPath`/`clientCertPath`/`clientKeyPath` on client endpoints); XSLT stylesheets (`xslt` fields and `xslt:` URIs); XSD schemas (`xsd` fields and `validator:` URIs); SQL files referenced by `sql:file:` URI operands (no `sql` document field exists); and static directory trees.
- Confine every asset reference to the selected compile root using the R1 source-resolution rules, expand static directories deterministically (symlinks inside a static tree fail closed), and embed asset bytes verbatim (binary-safe, no text normalization) as typed store entries under an `assets/` namespace with `store_schema: 2`. Deduplication by canonical target means alias spellings of one file map to a single store entry through a compile-time substitution table carried in the index; each table entry records its exact site — the byte span(s) in the normalized document or config entry — captured at compile time.
- Fail closed, before output creation, on: dynamic `${env:}` placeholders and absolute paths in asset fields and TLS URI parameters; file-valued secret fields; `wasm:` URI operands (the document `wasm` field is a security-policy registry NAME, not an embedded asset); embedded `Camel.toml` declarations of `[beans.<name>]` `plugin` entries or `[security.permissions.<name>]` WASM-provider `path` entries; and asset paths that escape the root, collide, or go missing. These `Camel.toml` classes and `wasm:` URI operands are R2-only deferrals (recorded in bd), not permanent rejections.
- Serve memory-served classes (static files — the only memory-served class in R2) from an in-memory asset registry populated before boot. Disk-written legacy consumers (TLS PEM loading in document fields and URI parameters, `xslt:` stylesheets, `validator:` schemas, `sql:file:` reads) receive a confined per-boot materialization under the file-ancestor-confinement precedent (bd `rc-0ks57`); runtime replaces only the index substitution table's recorded byte spans (last-offset-first) and never searches for, canonicalizes, or re-reads declared strings. No bulk extraction exists anywhere.
- Make the aggregate embedded-byte cap configurable with a compile-time option; the default stays 16 MiB, and cap enforcement moves with the knob.
- Extend the operational manifest to schema 3 with per-asset BLAKE3 digests and total embedded size; every asset entry carries a secret-material `class` (`public`/`secret`, documents implicitly public — `secret` is exactly the private-key family) and the manifest records `artifact_kind` (`job`/`server`; trailer route → `server`, job → `job`). Secret-class entries expose only digest and length — never contents, never key material in output or logs. `store_schema` 2 and `manifest_schema` 3 are a paired pair: a reader that accepts store schema 2 requires manifest schema 3, and vice versa.
- Require explicit opt-in for secret embedding: a secret-family asset (the private-key class — the `key` document field and the `tlsKey`, `serverKeyPath`, and `clientKeyPath` TLS URI parameters) fails compilation with a named diagnostic unless the operator passes `--embed-secrets`; with the opt-in, the artifact embeds the key and is written with file mode 0700 instead of 0755. Client-CA material is public and file-valued secret fields are rejected at compile, so neither is in the family; artifacts without embedded secrets keep 0755.

Affected crates: `camel-cli` (compile), `camel-dsl` (store schema), `camel-bundles` (asset registry and boot seams). Component crates remain unchanged; consumers outside this zone read through the registry or the documented confined materialization.

## Acceptance criteria

- Every enumerated asset class compiles into the store, boots, and is readable: static files from the in-memory virtual FS with no temporary files; disk-written classes from the confined per-boot materialization with byte-identical content.
- Materialized legacy consumers write only inside the confined per-boot directory (based under `std::env::temp_dir()`, random directory name, mode 0700; files mode 0600 created exclusively), with ancestor-confinement checks and cleanup at both shutdown and boot failure. SIGKILL, `process::exit`, or the in-tree force-exit on a second stop signal may leave residue; that caveat is documented, not silently ignored.
- The runtime substitution table in the store index records each (document, declared string) site's exact byte span(s) and its asset logical path; runtime replaces only those recorded spans (last-offset-first), percent-encodes values substituted into URIs, and never searches for or canonicalizes declared strings. Alias spellings of one canonical file map to one store entry.
- The aggregate cap is configurable at compile time, defaults to 16 MiB, and enforcement moves with it: under-cap compiles pass, over-cap compiles exit 2 with a named diagnostic and no usable output.
- Artifacts embedding a secret-family asset are written with mode 0700 only under the opt-in: secret embedding without `--embed-secrets` exits 2 with a named diagnostic and no artifact; with the flag it compiles and writes mode 0700; artifacts without embedded secrets keep mode 0755; `--manifest` output for secret entries shows only class, digest, and length — never key material.
- `./app --manifest` reports per-asset BLAKE3 digests and total embedded size without booting.
- Unknown store or manifest schemas (including schema-pairing violations), path escapes, duplicates, missing sources, symlinks inside static trees, dynamic placeholders or absolute paths in asset fields and TLS URI parameters, `wasm:` URI operands, secret-family assets compiled without `--embed-secrets`, and `Camel.toml` `[beans]` plugin or `[security.permissions]` WASM-provider-path declarations fail closed before boot or output.
- Read-only deployment: an artifact with no disk-written class writes nothing (beyond an explicitly requested report) under any filesystem; an artifact with a disk-written class boots on a read-only root when `TMPDIR` is writable; an artifact with a disk-written class and no writable temp location exits 2 before boot with a named diagnostic.

## Risk budget

Acceptable: `store_schema` 2 with `manifest_schema` 3 as a required pairing, a process-global in-memory asset registry, confined per-boot materialization for documented legacy consumers, and mode-0700 artifacts for private-key-bearing payloads. Deferred (R2-only, recorded in bd with epic `rc-rye74` rationale): `wasm:` URI-operand module embedding, `[beans]` plugin embedding, `[security.permissions]` WASM-provider-path embedding, and file-valued or literal secret-field embedding — each returns to its roadmap owner, they are not permanent rejections. Also deferred: deploy-side TLS material (mounted or rotated certificates) is out of R2 scope; R2 artifacts embed a fixed certificate set and an owner decision on deploy-side TLS material is tracked in bd. Out of bounds for R2: watch or hot reload, runtime file discovery, ambient configuration, a wider artifact argument surface, and any component-crate source edits. Compression (R6), signing (R4), and cross-target compilation (R7) are roadmap milestones, not permanent non-goals, and per-consumer byte-seam work in component crates is a recorded additive follow-up. Existing v1 and v2 (R1) artifacts remain readable.

Sealed owner ruling (bd `rc-p823t`, 2026-09-24, folded into these artifacts): TLS-class references resolve embedded-only with NO host fallback at compile or runtime, leaving the reference syntax free for R5 `host:`/`env:` prefixes; secret embedding is explicit opt-in via `--embed-secrets`; the accepted risk is named — an artifact embedding a private key IS a secret, extractable from the virtual store, and signing (R4) protects tamper, NOT confidentiality, accepted by the owner (kennycallado); and the manifest records `artifact_kind` now as an R3 tripwire: no long-lived artifact entries ship before the R5 TLS decision, and any artifact that can outlive a short bounded run triggers it.

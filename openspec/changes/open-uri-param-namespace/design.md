# Design: open-uri-param-namespace

## Approach

Add a typed pattern matcher to `UriOption` so the lint, schema-gen, catalog, and doc-gen
all see open namespaces as first-class metadata records. Use a small `#[non_exhaustive]`
enum — not a raw glob string — so the matcher is total, unambiguous, and extensible
without a Rust-side schema break.

The macro gets one new key. The lint's shared `resolve_option` helper is the only edit
point that affects all three rules (`ruriknown`, `rsecret`, `rdeprecated`). Match
resolution order is:

1. Exact-name match against `option.name`.
2. Exact match against any entry in `option.aliases`.
3. Pattern match across all `pattern: Some(_)` options, **longest separator wins** when
   multiple patterns match the same key (e.g. given patterns with separators `param.`
   and `param.foo.`, the key `param.foo.bar` resolves to the `param.foo.` option). A
   pattern match requires a non-empty suffix after the separator.

The `param.` separator with an empty suffix (bare `param.`) does NOT match — it falls
through to `UnknownOption`. This matches the runtime parsers in
`crates/components/camel-xj/src/config.rs` and
`crates/components/camel-xslt/src/config.rs`, which already skip empty suffixes via
`!param_key.is_empty()`. Lint and runtime agree.

The design rationale (alternatives comparison, edge-case analysis, schema-migration risk)
was produced by an `@experts/e_opus` consultation; see the bd `rc-2s7g` thread for the
full record. The verdict was Design A with a typed enum, rejecting the raw-glob, flag,
`OptionKind::Namespace`, and macro-only-catch-all alternatives.

## Affected crates

- **camel-api** (`crates/camel-api/src/component_metadata.rs`): add the `UriOptionMatch`
  enum and the `pattern` field on `UriOption`; add the `pattern_prefix` builder method;
  extend the `serde`/`schemars` annotations to keep the field optional-and-skippable;
  add unit tests covering match resolution, longest-prefix ordering, empty-suffix
  rejection, and serialization (both `Some` and `None`).
- **camel-endpoint-macros** (`crates/camel-endpoint-macros/src/uri_config.rs`): extend
  `UriParamAttr` with `pattern: Option<String>`; extend the `#[uri_param]` key parser
  (around the existing unknown-key check) to accept `pattern = "..."`; extend
  `build_uri_option_entry` to emit `.pattern_prefix(sep)` when present; add compile-time
  guardrails (field-type check, key-combination rejections, empty-separator rejection).
- **camel-lint** (`crates/camel-lint/src/route_view.rs`, `resolve_option`): extend the
  match predicate so that, after the existing exact-name and alias checks fail, the helper
  tries each `pattern::Prefix` option with a non-empty-suffix requirement, ordered by
  descending separator length. Add tests in `ruriknown.rs` covering: `param.foo` resolves
  when the scheme has a `Prefix { separator: "param." }` option; bare `param.` does not;
  discrete-name collision favors the discrete option; overlapping prefixes resolve to the
  longest separator.
- **schemas/component-metadata.json**: regenerated by `cargo xtask schema --check`. The
  schema gains an optional `pattern` property on `UriOption` and a new `UriOptionMatch`
  definition. `schema_version` stays at 1 (no breaking change; the field is optional and
  the catalog is harvested in memory, with no on-disk persistence layer to migrate).

## Serialization contract

The `UriOptionMatch` enum uses Rust's default **externally-tagged** serde representation
with `#[serde(rename_all = "snake_case")]` on the enum and on the `Prefix` struct
variant's field. Concrete JSON shape for `Some(Prefix { separator: "param." })`:

```json
{
  "name": "param",
  "description": "...",
  "kind": "string",
  "pattern": { "prefix": { "separator": "param." } }
}
```

When `pattern` is `None`, the field is omitted (`#[serde(default, skip_serializing_if =
"Option::is_none")]`), so existing `UriOption` JSON is byte-identical.

The JSON Schema artifact (`schemas/component-metadata.json`) gains an optional `pattern`
property of type `object` with a one-of referencing the `UriOptionMatch` definition
(initially a single `prefix` variant). `schemars` infers optionality from the Rust
`Option<T>` type, so the schemars annotation only needs `#[cfg_attr(feature = "schema",
schemars(default))]` matching the existing optional-field pattern in `component_metadata.rs`.

**No TypeScript artifact is currently exported** for `ComponentMetadata` (verified: the
`ts_rs` derive exists on the struct, but `cargo xtask` does not generate or commit a
`.ts` file for it). Change 1 does not introduce a TS export; if a future change adds
one, the `UriOptionMatch` union will surface as a TypeScript discriminated union, which
each future variant expanding.

## Architecture boundaries

This change touches the metadata/control plane only. No data-plane processor, DSL
runtime, or endpoint creation path is changed. The `Component` trait signature is
unchanged.

The macro extension is additive at the authoring surface (a new opt-in key, with default
behavior preserved). The `UriOption` struct extension is additive at the contract surface
(one optional field with `skip_serializing_if`). The lint change affects validation logic
only (one helper predicate), not the rule registry, the engine, or the schema.

The hexagonal boundary is respected: `camel-api` defines the contract,
`camel-endpoint-macros` generates the metadata at compile time, `camel-lint` consumes it.
No new dependency edges are introduced; specifically `camel-lint` does not gain a
dependency on `camel-endpoint-macros`.

## Phases (optional)

Omitted. This is a single coherent slice (contract + macro + lint + docs land together).
No milestone grouping benefit; `tasks.md` will not use `## Phase N` headings.

## Alternatives considered

**A' Raw glob string** (`pattern: Option<String>` like `"param.*"`): rejected. Requires a
glob matcher dependency and adds match-time ambiguity (does `param.*` match `param.foo.bar`?).
The typed enum avoids both.

**B `open_namespace: bool` flag + `name = "param"` convention**: rejected. Couples matching
to a magic string; cannot distinguish a discrete option literally named `param` from the
namespace; silently assumes `.` separator. The typed variant carries the separator
explicitly.

**C `OptionKind::Namespace` variant**: rejected. `OptionKind` is the value-type axis
(String/Int/Bool/Duration…). Structure (scalar vs namespace) is orthogonal; conflating
them forces every `match OptionKind` site to special-case a variant that carries no value
semantics. The issue text itself diagnosed this as a category error.

**D Macro-only catch-all** (`#[uri_param(catch_all)]` that emits no `UriOption`): rejected.
Breaks the single-source-of-truth invariant established by `rc-4cos` — invisible to
schema-gen, doc-gen, catalog. Cannot carry `description`, `kind`, or `deprecated` for the
namespace, which the runtime parsers' own docstrings already describe.

**Honest cost of the chosen design.** The typed enum stabilizes the Rust-side matcher
shape (via `#[non_exhaustive]`) and avoids the stringly-typed traps above. However, each
future `UriOptionMatch` variant (e.g. `Glob`, `Regex`) expands a closed JSON-Schema union
and any generated TypeScript discriminated union. Stale validators and exhaustive
generated consumers may reject the new variant at parse time despite the Rust-side
forward-compat guarantee. Each future variant therefore requires a schema compatibility
review and regenerated downstream consumers. This cost is preferable to the rejected
alternatives, which either paint us into a corner (B, C) or re-create the two-truths
failure mode (D). It is not zero, and it is recorded in the proposal Risk budget.

For the full comparative analysis (including schema-migration risk, edge cases, and
the chosen migration shape for `xj`/`xslt` in Change 2), see the `@experts/e_opus`
consultation referenced in bd `rc-2s7g`.

## Answers to the 4 questions

1. **Architecture — right shape.** `OptionOrigin` (Query/StepParameters/ConfigParameters)
   is a clean bijection with the two lowering fail-closes and carries no scheme/catalog
   coupling — it lives on `LintOption` where the span already lives. `duplicate-key` as a
   `UriKnownSubCode` (not a new rule) is correct: it shares R-URI-known's per-endpoint walk,
   its "runs before catalog lookup" placement, and its option vocabulary; a new rule would
   duplicate the endpoint iteration and the pre-parse guard. Message vocabulary ("the URI
   query string"/"step parameters"/"config parameters") is fixed and lowering-ordered.
   Span-on-redundant-occurrence (first non-query) matches the side the lowering blames in
   BOTH fail-closes (params key for query overlap; step key for config/step overlap). No
   regrettable coupling. `#[non_exhaustive]` on the enum is future-proof.

2. **Semantic completeness — mirror is faithful.** The lowering reaches a fail-close at
   exactly 5 sites: `from` (route 1 + routes 2..N), `to`, `wire_tap`, `enrich`, `poll_enrich`
   (yaml.rs 550/668/680/1351/1364). All 5 carry a step-level `parameters:` that
   `walk()` attaches via `effective`; enrich/poll_enrich additionally get the config-side map
   (ConfigParameters). **Verified `wire_tap` step-params overlap fires** (probe). URI_KEYS
   also lists `endpoints` (scatter_gather) and `dead_letter_channel` — both structs have NO
   `parameters` field and use `deny_unknown_fields`, so they can never reach either
   fail-close; the lint correctly never emits `duplicate-key` for them (over-listing is inert
   here, and is right for the other sub-codes). JSON DSL: lint uses `cst::parse_document`
   which is format-agnostic over the noyalib CST, so JSON routes are covered by the same walk.
   Templated routes: `{{...}}` substitution runs on materialized JSON *before* route AST
   deserialize (materializer.rs), so the lint never sees template bodies as routes — no
   bypass, no double-report; a literal `?k={{p}}` is treated as key `k` by both lint and
   lowering, identically. `from` only route-1 in the `from` slot is a pre-existing, tested
   design (rc-m1mx); routes 2..N `from` fall through to the URI_KEYS path *with* `effective`,
   so their overlaps are still flagged.

3. **Implementation failure modes — none found.** `flag_cross_source_duplicates` groups on
   `&str` raw keys in a BTreeMap: **non-ASCII key (`café`) produces one diagnostic, no panic**
   (probe) — byte-span slicing is on a char boundary because keys are whole YAML/query tokens.
   **Value-less query flag (`?daemon`) vs `parameters{daemon}` fires** (probe), mirroring the
   lowering's whole-token query key. `sources.len() < 2` guard + `first_non_query` total-not-
   `expect` path means no unwrap and no wrong-count. One diagnostic per colliding key per
   endpoint (all-three-sources test). Repeated raw-query keys stay legal (test).

4. **Merge readiness — no hold.** All gates green post-rebase; corpus baseline byte-identical;
   the final commit adds only ledgers. The `.review-eopus-holistic.md` (this file) should be
   force-added alongside the existing ledgers per the change-dir convention.

## Findings

- **[minor]** ruriknown.rs:57-65 — the doc-comment on `flag_cross_source_duplicates` says
  "options arrive ordered query-first, then step-level parameters, then config parameters"
  but the config/step ordering (`inherited=step ++ local=config`) is only established in
  document.rs `walk()` line 382, not restated here. Correct today; a future reorder of that
  concat would silently move the span from the step key to the config key with no failing
  test (the all-three-sources test asserts count, not span side). Suggest a one-line assert
  in a test that with all three sources present the span lands on the **step** key, to pin
  the contract. Non-blocking; fold into the existing rc-aqxo P3 follow-up.
